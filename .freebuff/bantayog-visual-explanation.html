Bayanihan Finance · WOCEE 2026 · SparkFest 2026

BANTAYOG

LGU nutrition cash grants → nutrition-locked subsidies for the Philippine "First 1,000 Days" cohort. A printed QR Nutri-Pass replaces cash; credits are spent only on child-appropriate food at approved sari-sari stores, settled on Polygon Amoy testnet.

1. System Overview

One Next.js 16 PWA serves three surfaces, sandboxed by hostname. The web app is a view layer only — all business logic lives in the Hono 4 API server.

🏛️ LGU Admin

Routes: /login, /admin/*

Auth: Supabase email+password, role === 'admin'

Registration, tier computation, one-time allocation, QR pass issuance.

📱 Merchant POS

Routes: /merchant-login, /dashboard, /cart/*, /checkout

Auth: password on derived email <mobile>@merchant.bantayog.local

Product scan, cart, PIN verification, checkout via settle_sale.

👁️ Balance View

Route: /balance?token=...

Auth: none — the signed QR token is the authorization.

Read-only: shows balance + last 50 transactions.

📃 Printed Nutri-Pass

The only interface for beneficiaries. No login, no app.

Two QR codes: one JWS token for payment, one URL for balance view.

2. Layer Stack

The server follows a strict layered architecture. Each layer has one responsibility.

🌐 apps/web Next.js 16 PWA — view layer only, no business logic
🚪 Routes HTTP boundary — validates with zValidator, maps errors to status codes
🗂️ Services Orchestration — returns AppResult<T>, no HTTP types
🧮 Domain Pure functions — injectable currentDate, no I/O
🗄️ Repositories One class per table — extends BaseRepository, no policy
📋 DTO / Mappers snake_case ↔ camelCase — the only translation point
⛓️ Lib / Gateways Errors, Logger, Supabase, Redis, Gemini, viem (chain client)
🏗️ Architecture rules
  • Route never talks to Supabase for a business decision.
  • Service never imports a Hono type and never throws for an expected failure.
  • Repository holds no policy — it reads and writes rows.
  • Domain function has no I/O — receives currentDate as an argument.
  • apps/web holds no decision — server copy always wins.

4. Core Flows

4.1  Beneficiary Registration (Admin)
1
Guardian provides details
Name, mobile, child name, age, monthly income, GPS location, card serial, 6-digit PIN
2
PIN hashed (Argon2id)
PIN is never stored in plaintext. @node-rs/argon2 produces the hash and salt.
3
Tier computed
computeTier(currentDate) — Tier 1 (Critical) if age ≤ 1,000 days from conception (≤ 730 days from birth), else Tier 2 (Standard). Pure function.
4
Custodial EVM wallet generated
A beneficiary wallet is created. Private key stored as AES-256-GCM ciphertext — never stored or logged in plaintext.
5
Signed QR token generated
JWS compact JWT embedding beneficiaryId, walletRef, tier, childName, guardianName.
6
Nutri-Pass printed
Two QR codes: one JWS token for payment, one URL for balance view. Printed on the physical card.
4.2  Product Scan → Cart (Merchant)

Branded Items

1
Capture photo
Merchant photographs a branded product through the camera viewfinder.
2
POST /api/vision/analyze-scan
Gemini analyzes the image. Returns: blurry | unrecognized | identified, child-friendliness verdict, flagged ingredients, category, and researched PHP base price.
3
Product upsert
Identified products are upserted into products catalog. Price range = base ± 10, eligibility from verdict, category defaults to Draft when unknown.
4
Review & add to cart
Merchant reviews AI analysis, adjusts price/quantity, then adds to cart.

Non-Branded Items (Palengke)

1
Capture photo + manual entry
Merchant captures a photo of the produce and enters product name, price, and unit (per kilo, per piece, etc.).
2
POST /api/vision/validate-non-branded
Gemini validates the image + manual entry against market_prices reference data. Returns: justified/unjustified verdict, child-friendliness, and market price range.
3
Add to cart
Only if AI validation passes (justified + child-friendly).
🎯 Eligibility rule

Eligibility always comes from the products catalog, never from the AI model directly (ADR-003). The AI guides, the catalog decides.

4.3  Checkout — The Critical Money Path

This is the most important flow in the system. Every step is ordered and guarded.

1
Merchant is APPROVED
Only APPROVED merchants can create transactions. PENDING | REJECTED | SUSPENDED merchants are rejected.
2
Verify QR token (JWS HS256)
The signed JWT from the Nutri-Pass is decoded and verified. Rejects invalid/expired tokens.
3
Check qr_passes.expires_at
⚠️ Known gap: revoked is NOT checked here — only checked in POST /api/auth/verify-qr.
4
Beneficiary not SUSPENDED / INELIGIBLE
Blocked statuses prevent the transaction.
5
Verify guardian PIN (Argon2id + lockout)
6-digit PIN checked against stored hash. Lockout prevents brute-force (Upstash Redis).
6
Validate total > 0
Reject non-positive purchase amounts.
7
Check sufficient credit balance
Compare total against beneficiaries.credit_balance.
8
settle_sale RPC — atomic money movement
SECURITY DEFINER Postgres function. Does SELECT ... FOR UPDATE on beneficiary, deducts credit, credits merchant, inserts transaction as CONFIRMED.
⚠️ Known gaps in checkout
  • revoked not checked: qr_passes.revoked is only checked by POST /api/auth/verify-qr, not by checkout.
  • No outbox row written: The live checkout path writes no outbox row. The reconcile cron has nothing to drain from a real sale.
  • Response assembled in memory: totalCreditDeducted, stablecoinAmountWei: '0', and confirmedAt are computed locally but not persisted by settle_sale.
4.4  Chain Settlement — Cron Reconciliation

A scheduled cron job (via cron-job.org) drains the outbox and settles on-chain.

1
POST /api/cron/reconcile
Bearer CRON_SECRET authentication. Loads chain config via loadChainConfig.
2
Claim up to 20 outbox rows
status = PENDING, kind = TRANSACTION_CHAIN_SUBMIT. Each row updated to PROCESSING.
3
Transfer PHPC on-chain
Treasury → merchant wallet via ERC-20 transfer. Waits for confirmation receipt.
4
Success → DONE + CONFIRMED
Outbox = DONE, transaction = CONFIRMED with onchain_tx_hash.
5
Failure → retry up to 3 → FAILED
At 3 attempts: outbox = FAILED, transaction = FAILED. Balance-restoration compensator writes BALANCE_RESTORATION_AUDIT.
4.5  One-Time Allocation
1
Admin triggers allocation
POST request for a specific beneficiary.
2
Tier computed → amount derived
computeTier(currentDate) → Tier 1 = 5,000 PHPC, Tier 2 = 3,500 PHPC. Amount never from request body.
3
Insert allocations row
beneficiary_id UNIQUE is the idempotency guard — each beneficiary gets one allocation.
4
Chain allocateCredits
Calls PHPCSubsidy.allocateCredits(keccak256(beneficiaryId), amountWei). Waits up to 60s for confirmation.

💰 Money model

PHP with 2 decimals → NUMERIC(12,2) in Postgres. Integer credits on-chain. 1 credit = 1 PHPC = 1e18 wei. Cash-out converts with BigInt(Math.round(amount * 100)) * 10n ** 16n. No floats in credit math.

7. Money Flow

⚠️ Known ADR drift
  • ADR-001 says: handler writes tx + outbox row atomically, returns PENDING_CHAIN. Code today: live checkout writes no outbox row, returns CONFIRMED.
  • ADR-001 says: contract de-duplicates with transaction UUID. Code today: reconcile cron sends plain treasury-to-merchant transfer, doesn't call processTransaction.
  • Status drift: Only 3 of 5 statuses are written: PENDING_CHAIN (TransactionService), CONFIRMED (settle_sale + cron), FAILED (cron). Never SUBMITTED or RECONCILED.

8. Transaction Status Machine

💡 Observability note

Only 3 of 5 statuses are actually written: PENDING_CHAIN, CONFIRMED, and FAILED. SUBMITTED and RECONCILED are defined but never set. This means you cannot distinguish an off-chain settlement from a chain-confirmed one by status alone.

🔐 Security highlights

  • PINs: Argon2id hashed, never stored in plaintext
  • Wallet keys: AES-256-GCM ciphertext at rest
  • QR tokens: JWS HS256 signed
  • Rate limiting: Upstash sliding window
  • PIN lockout: Upstash Redis
  • Server uses service role key — bypasses RLS (defense in depth)

🚫 Never do

  • Wire a mainnet key or mainnet RPC
  • Reimplement balance math in TypeScript (use settle_sale)
  • Write DB_RECORDED or BROADCAST to transactions.status
  • Add mutating capability under /api/balance
  • Commit .env* files
